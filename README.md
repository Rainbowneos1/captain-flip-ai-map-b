# b-web —— 《航海争夺》人机对战网页（地图 B，纯本地、无服务器）

把训练好的**地图 B** 策略网络量化压缩后内联进网页，做成一个可以像原热座网页那样直接
双击打开的人机对战页面：初始界面选先后手、可随时打开规则说明，AI 的**每一次决策都会
展示出来并至少停 1.2 秒**。

```
双击 index.html 即可开玩 —— 不需要任何服务器、不需要联网、不需要构建步骤。
```

### 1.1 最少需要几个文件？

**一个 html + 三个 js，放在同一个文件夹里就够了**（无子目录、无服务器、无构建、无网络）：

```
你的文件夹/
├─ index.html      ← 双击这个
├─ game.js         ← 引擎（必须先于下面两个被 <script> 载入，见下）
├─ weights.js      ← 量化权重，体积都在这里
└─ ai.js           ← 反量化 + 前向推理
```

* `index.html` 里只有三条相对路径的 `<script src>`，顺序为 `game.js → weights.js → ai.js`
  （`game.js` 挂 `window.CFS`，`weights.js` 挂 `window.CFS_MODEL`，`ai.js` 挂 `window.CFS_AI`；
  三者都在加载时只做定义、不互相调用，所以顺序其实只要保证都在 body 结束前即可）。
* **不能**用 ES module / `fetch`：`file://` 协议下浏览器会以 CORS 为由拒绝加载模块与 fetch，
  所以这里刻意全部用普通 `<script src>` 并把权重直接挂到 `window` 上——这正是"不依赖服务器"的前提。
* `export_weights.py` 与 `verify/` **不是运行必需的**，只是导出工具与验证脚本，删掉不影响游玩。
* 已实测：把上述 4 个文件复制进一个空文件夹（另加一个测试驱动脚本），用 `file://` 打开、
  无头浏览器合成点击**完整打完一局**，页面 0 报错。见 §5.5。

## 2. 玩法与流程

1. **开局界面**：① 选择 **我先手**（你执玩家 1）或 **AI 先手**（你执玩家 2，AI 执玩家 1）；
   ② 地图固定为 **地图 B**（附 5 列预览与「先完成者 / 后完成者」分值）；
   ③ 「📖 游戏规则」按钮弹出规则说明（含地图 B 的 5 列表格，可用 ✕ / 点遮罩 / Esc 关闭）；
   ④ 开始对局。
2. **对局界面**：左右两块棋盘（行 0 在最下，与原热座网页相同的摆法与图标）、列奖励图标行
   （地图 B 全部是 🏅 = `first_complete`）、分数、当前行动方高亮、底部对局记录。
3. **你的回合**：抽牌后二选一「保持朝上面放置 / 翻面查看（不可逆）」——选翻面会先把新的一面
   展示给你，再点「放置此方块」确认；然后点击任意一个高亮的列，方块落在该列最下面的空格；
   猴子效果会让你点一个高亮的相邻方块。**你只能看到朝上的一面**，另一面不可见。
4. **AI 的回合**：AI 抽牌、翻面、选列、翻猴子，每个决策点都有一行 `🤖 AI 决策：…`，
   写清它做了什么（翻了哪一面、放到第几列、列奖励是什么、翻哪个相邻格），
   并**至少停 1.2 秒**；若这次网络推理本身耗时超过 1.2 秒，就不再额外等待
   （实际推理约 1 ms，所以正常情况下都是停满 1.2 秒）。
5. **结算**：角色效果、列奖励（地图 B 的 `first_complete` 先/后完成者分值）、终局计分
   （瞭望员/木匠/鹦鹉/水手）、炮手 ≥3 判负且记 0 分 —— 全部按现行规则实现；
   结束时给出胜负、终局分数、炮手数、完成列数，并提供「再来一局 / 重新选择先后手」。

### 2.1 地图 B 的规则（页面里的规则弹窗必须与此一致）

棋盘 5×5，只用到地图划出的 5 个竖直列；**行 0 = 最下**，方块总是落在该列**最下面的空格**。
每列的奖励是 `first_complete`：**全局限定的**「先完成者 / 后完成者」分值。

| 列 | `rows`（自下而上） | 格数 | 列奖励 |
|---|---|---|---|
| 第 1 列 | 0, 1 | 2 | 先完成者 **+1**，后完成者 **+0** |
| 第 2 列 | 0, 1, 2 | 3 | 先完成者 **+2**，后完成者 **+1** |
| 第 3 列 | 0, 1, 2, 3, 4 | 5 | 先完成者 **+6**，后完成者 **+3** |
| 第 4 列 | 0 | 1 | 先完成者 **+0**，后完成者 **+2** |
| 第 5 列 | 0, 1, 2, 3 | 4 | 先完成者 **+4**，后完成者 **+2** |

> **两处容易看错、但确实是设计如此的地方**：
> 1. **「先完成者」按全局的该列完成顺序判定**，与「谁先完成自己的这一列」无关 ——
>    第二个把自己的这一列填满的人（无论哪个玩家）拿 `second` 值。`finished[col] = True`
>    发生在结算**之前**。
> 2. 第 1 列先完成 **+0**、第 4 列先完成 **+0**，不是漏写；这两列的价值全在"后完成也能拿分"
>    以及"抢在对手前面把列占掉"的阻塞意义上。

## 3. 权重压缩

**量化方案**：`per-group 对称 8bit`（`export_weights.py`）

* 只压 2D 权重矩阵；**沿输入维每 `group` 个数为一组**，每组独立求 `scale = max|w| / 127`，
  存 `round(w/scale)` 到 `[-127, 127]`。组内共用一把 scale ⇒ 组越小越精确、scale 开销越大。
* 偏置与所有 1D 参数保持 fp32（全部加起来 550 个数 ≈ 2 KB，压了没意义还伤精度）。
* 输出 `weights.js`：每个张量 = `{shape, g, sc:(base64 fp32 scales), d:(base64 int8)}`。
* **反量化在网页加载时一次性完成**（`ai.js: dequantize()` → `Float32Array`），
  推理全程 fp32，所以推理路径与 torch 的差别**只**来自量化本身。

| 项 | 数值 |
|---|---|
| 参数量 | 228,901（`trunk.0` 256×599、`trunk.2` 256×256、4 个决策头 2/5/4/25、`value`） |
| fp32 原始大小 | 894.1 KB |
| 量化载荷 | 232.4 KB（int8 权重 + fp32 分组 scale） |
| **`weights.js`（base64 后）** | **311.3 KB**（318,762 字节）→ **压缩比 2.87×** |
| 相对重建误差 | max 0.0039（7 个矩阵全部）；组大小从 8 到 128 都是 0.0039（= 1/255 量级） |

### 3.1 量化到底损失了多少？（都实测过，不是估计）

**(a) 反事实动作一致率**：让 fp32 策略自己对局，在它遇到的每个**多选**决策点上再问一次
「量化网络会选什么」（`verify/quant_sweep.py`，同一批状态、可复现）：

| group | 8 | 16 | 32 | 64 | **128（本页采用）** |
|---|---|---|---|---|---|
| 动作一致率 | 99.64% | 99.50% | 99.24% | 99.14% | **98.86%** |
| `weights.js` 体积 | 449 KB | 375 KB | 338 KB | 320 KB | **311 KB** |

（每组 24,198 个多选决策点，另有 775 个单选决策点跳过；反事实一致率 = 在 fp32 自己遇到的状态上，int8 与 fp32 选出同一个动作的比例。）

**(b) 头对头胜率**（真正的验收：int8 策略 vs fp32 策略，交替坐先/后手）：

| group | int8 vs fp32 胜率（3000 局） | 相对 0.5 的 z | 判定 |
|---|---|---|---|
| **128** | **0.4903 ± 0.009**（1469 胜 4 平 1527 负） | −1.08 | 与 0.500 不可区分 |
| 64 | 0.4947 ± 0.009（1483 胜 2 平 1515 负） | −0.59 | 同上 |
| 32 | 0.4947 ± 0.009（1483 胜 2 平 1515 负） | −0.59 | 同上 |
| 16 | 0.4935 ± 0.009（1479 胜 3 平 1518 负） | −0.72 | 同上 |
| 8 | 0.4948 ± 0.009（1483 胜 3 平 1514 负） | −0.58 | 同上 |

**结论**：取最省的最小文件 —— **`group = 128`**。把组从 128 缩到 8（体积 **+45%**）只把决策一致率从 98.86% 抬到 99.64%；而**五个组在 3000 局头对头里全都测不出相对 fp32 的胜率损失**（全部落在 0.490–0.495，最大 |z| 只有 1.08，且**顺序不单调** —— 64/32/8 挤在 0.494–0.495，128 反而最靠下）⇒ 这些差异是噪声，不是“组越小越好”。既然本页的主要目标是压体积，就直接取最省的 **group = 128**。

> 附带一条观察：地图 B 的一致性（**98.86%**）比地图 A（99.41%）**略低**，说明这个网络对权重量化更敏感一点；但 3000 局头对头照样测不出差别 —— 这正好说明“一致率”只是过程指标，**头对头胜率才是验收指标**。

> ❌ 衡量量化代价**绝不能**用"重放整局时的逐决策一致率"：第一个决策分歧之后，后面每一步
> 都在比较两个不同的局面，数字会虚高（地图 A 实测虚高到 98.80%，真实是 99.4–99.6%）。
> 一定要用**反事实一致率**（同一批状态）或**头对头胜率**。

### 3.2 重新导出（换检查点 / 换组大小）

```bash
python b-web/export_weights.py --ckpt runs/b-r4/final.pt --group 128
```

当前 `weights.js` 来自 `runs/b-r4/final.pt`（iter 1000）（`use_belief=true`、`dim=599`、`hidden=256`、`layers=2`）。
**换检查点或换 group 之后必须重跑闸门 3**（§5.3），因为 `py_trace.json` 是按**同一份权重**
复算出来的 —— 这条规矩在本项目里**实际执行过三次**（`b-r1` → `b-r3` → `b-r4`），
每次都重导出 + 重跑全部闸门。

> **为什么交付点是 `b-r4`（以及它为什么不比 `b-r3` 更“确定”）？**
> 选点只看**留存块头对头**，不看训练轮数，也不看对脚本基线的胜率；而且**每一格都要 4 个留存块
> 合并成 4000 局**才读数 —— 因为地图 B 每轮的真实增益只有 1–2 pp，**单块 1000 局的尺子
> （SE 1.58 pp）根本看不见它**（这是本项目修正过的一个方法论错误，见
> `reports/地图B训练报告.md` §7.2，工具是 `tools/holdout_pooled.py`）。
>
> | 相邻两代 | 对手来源 | 四块合并胜率（4000 局） | z | 每轮增益 |
> |---|---|---|---|---|
> | `cont5-main` → `b-r1` | 热启动 + 地图适配 | **0.743 / 0.741**（两块各 1000 局） | +15.4 / +15.2 | 大额 |
> | `b-r1` → `b-r2` | 同课程续轮 | 0.5170 | +2.15 | +1.7 pp |
> | `b-r2` → `b-r3` | 对手池 = `b-r1`+`b-r2` 等比例混合 | 0.5102 | +1.30 | +1.0 pp |
> | `b-r3` → `b-r4` | 对手池里加**最佳响应利用者** | 0.5075 | +0.95 | +0.7 pp |
> | **`b-r1` → `b-r4`（累计）** | 三轮 | **0.551**（单块 1000 局） | **+3.23** | **+5.1 pp** |
>
> **如实说明**：`b-r4` 相对**当前交付点 `b-r3`** 的 +0.7 pp **没有达到统计显著**（z=0.95，
> 置信区间约 [0.492, 0.523]）。选 `b-r4` 的理由是：① 它相对**上一个已交付点 `b-r1`** 有
> **+5.1 pp、z=+3.23** 的显著优势；② **没有任何一块测量显示它比任何一代更差**（四代点估计单调不降）；
> ③ 换交付点只需重导出 + 重跑闸门（约 20 分钟）。
> **若你偏好“只在显著胜过当前交付点时才换”的保守口径，该交的是 `b-r3`** ——
> 两者实测差 ~0.7 pp，都在噪声尺度内；`b-r3` 的导出参数（group 128）在报告 §7.4 有完整记录。
>
> **更重要的结论是这三个杠杆一起给出的**（报告 §7–§8）：**“换对手来源”这条轴已经吃完** ——
> 同式续轮 +1.7 pp、两代混合 +1.0 pp、放入最佳响应 +0.7 pp，**单调递减到与 0 不可区分**；
> 而且**最近几代不可被同类别最佳响应利用**（250 轮专精的利用者只有 0.488，
> 1000 轮专精反而降到 **0.443 / z=−7.24**）。要继续变强得换**容量或特征**，
> 那是需要从零重训的长周期路线（算力账见报告 §9）。好消息：`ai.js` 是**架构无关**的，
> 将来换更大网络**网页端一行都不用改**。

## 4. 为什么引擎/特征要用 Python 那一套

AI 是照着 `cfs/encode.py` 的 599 维特征训练的，其中最后 19 维是**牌堆均值场后验**
（`P(背面=r | 正面=T)` 的 8 维、剩余朝上面期望 9 维、期望剩余总数 1 维）。网页里必须
**一模一样**地复现它，否则 AI 会看到它没见过的输入。因此：

* `game.js` 里的 `Game` 用**生成器**复刻 `cfs/engine.py` 的协程结构（鹦鹉嵌套回合、
  猴子连锁翻面都靠 `yield`），决策点协议（flip / col / monkey）与 Python 完全一致；
* `MeanFieldBelief` 是 `cfs/belief.py` 的均值场方案的逐行移植（软移除台账 + 完整对修正）；
* `BeliefDriver` 只从**公共视图序列**推出信念事件（同样不读牌堆），保证没有隐藏信息泄漏；
  注意它必须拿到**本地图的列定义**（`game.columns`）才能把「列动作」还原成落点行 ——
  地图 B 传错成地图 A 的列定义会**静默**算错信念特征（见 §7.2）；
* 列几何与列奖励全部来自 `game.js` 顶部唯一的 `MAP_B` 常量，与规则保真源
  （项目根的 `index.html`）逐字段一致；
* 结局与计分按**现行规则**（`boomRule="lose"`：炮手 ≥3 判负且该方记 0 分）。

### 5.3 策略逐决策对拍（`verify/dump_python_trace.py` + `verify/check_policy_vs_python.mjs`）

**这是最重要的一道闸门**：它同时验证**引擎 + 信念 + 特征编码 + 量化前向**四件事。
Python 侧用**同一份量化权重**（numpy 复刻）跑 10 局完整对局并逐决策落盘；网页侧用同一抽牌顺序
重放，逐项比对 **特征向量（599 维）/ 头部 logits / argmax 动作 / 终局 digest**：

```bash
python b-web/verify/dump_python_trace.py --games 10 --qgroup 128 --map B
node   b-web/verify/check_policy_vs_python.mjs
# → [check] 决策点总数 507，动作不一致 0，整局不一致 0/10
```

## 6. 已知取舍

* **只支持地图 B**（按需求）。引擎里保留了其它地图的列奖励与机制分支，但未实现地图 G 的囚徒区、
  地图 E 的 `flip_tile`，遇到会显式抛错而不是静默出错。
* **量化是有损的**：约 **1.14%** 的决策会与 fp32 网络不同（反事实一致率 98.86%，24,198 个多选决策点），但 **3000 局头对头测不出胜率损失**（0.4903 ± 0.009，z = −1.08，与 0.500 不可区分）。这是需求里明确接受的代价。
* **地图 B 的先完成者语义是"全局"的**（见 §2.1 注 1）。这一点在四个引擎里都必须一致，
  任何一处写成"谁先完成自己的这一列"都会导致训练/网页规则分歧 —— 已由闸门 2 与闸门 3 锁住。
* 牌堆耗尽时按原规则**重建整副新牌堆**（`index.html` 行为）；`jsref` 参考引擎为了对拍
  不重建而是报错，这是两边**已知且有意**的差异（对拍脚本会给足 300 张牌）。
* AI 用确定性 argmax（与训练评估口径一致），不复现采样带来的多样性。

## 7. 修复记录

### 7.1 对局记录的归属错位（沿用地图 A 的修复，本部署已包含）

**现象**：日志里「你抽到…」其实是 AI 抽的，「AI 抽到…」其实是你抽的。

**根因**：引擎的一次 `game.step()` 并不只做"当前玩家的这一步"——它在结束当前回合后
**会继续一路推进到下一位玩家的第一个决策点**（决策点协议就是这么设计的），于是同一批事件里
同时包含当前玩家本步的事件与**下一位玩家的 `draw`**；终局计分更会一次性抛出双方的计分事件。
旧代码按"刚刚是谁在行动"给整批事件打标签，于是全错。

**修复**：归属改为**按事件自带的玩家** `ev.p`。由 `verify/check_log_attribution.mjs` 锁住。

### 7.2 地图 B 移植期修掉的三处（本次）

1. **`export_weights.py` 的 `--out` 默认写死参考部署目录**
   （原为 `os.path.join(ROOT, "web-hva", "weights.js")`）：在 `b-web/` 里导出会把权重**写回
   地图 A 的部署目录**。已改为按脚本自身位置推导（`DEPLOY = dirname(abspath(__file__))`），
   `--ckpt` 默认改为当时的交付检查点（现为 `runs/b-r4/final.pt`）。模板 `web-hva/export_weights.py` 一并修正，
   并复跑确认地图 A 的产物**字节不变**（SHA256 相同）。
2. **`verify/dump_python_trace.py` 与 `verify/quant_sweep.py` 没有把地图透传下去**：
   既没给 `Game(...)` 传 `map`，也没给 `BeliefDriver` 传本地图的列定义
   （它默认是地图 A 的列）。结果是信念驱动会把「列动作」还原到错误的落点行 ——
   更糟的是它**不会报错**，只会让信念特征悄悄偏离训练分布。已给两个脚本都加上
   `--map`（缺省从检查点 `args.map` 恢复）并传 `game.columns`。
   同时 `check_vs_jsref.mjs` 的两处 `map: 'A'` 改为 `'B'`，`run_all.ps1` 的闸门 3 步骤
   带上 `--map B`。
3. **`.ps1` 里的非 ASCII 残留**：`run_all.ps1` / `run_page_smoke.ps1` 的注释行里带着中文路径，
   而 Windows PowerShell 5.1 会把无 BOM 的 `.ps1` 按 GBK 解码 —— 中文字节**有可能吞掉下一行
   命令**（本项目在别处踩过）。已把这几个注释改成纯英文，现在 `b-web/verify/*.ps1` 与
   `web-hva/verify/*.ps1` 经逐字节检查**全部是 ASCII-only**。

### 7.3 移植期的两条操作纪律（血泪）

* **不要用 PowerShell 的 `Get-Content`/`Set-Content` 管道改写 UTF-8 源文件**。5.1 默认按 ANSI(GBK)
  解码，中文被错配后其尾字节会与紧跟的 `\r` 组成非法序列、**连换行一起吃掉**，文件会静默损坏
  （本次在 `game.js` 上踩到一次，靠"从参考部署重拷 + 重做编辑"恢复）。
  需要批量替换就写一个 **Python** 一次性脚本，并对每处替换先断言 `count(old) == 1`。
* **`.ps1` 一律 ASCII-only**；中文清单文本交给 Python 写。
